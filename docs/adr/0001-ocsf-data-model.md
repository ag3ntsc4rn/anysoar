# ADR 0001: OCSF as the data model

- **Status:** accepted
- **Date:** 2026-10-15

## Context

Agents need one vocabulary for alerts, cases, indicators and enrichment that works whichever
SOAR is underneath. Inventing our own schema would mean defining, documenting and defending
every field ourselves, and every driver author would have to learn it. The
[Open Cybersecurity Schema Framework](https://schema.ocsf.io) (OCSF) is an open,
vendor-neutral schema that already covers most of this.

## Decision

anysoar's models are Pydantic v2 models of **OCSF 1.9.0** classes and objects:

| anysoar concept | OCSF |
|---|---|
| alert | Detection Finding, class 2004 (`DetectionFinding`, alias `Alert`) |
| case | Incident Finding, class 2005 (`IncidentFinding`, alias `Case`) |
| indicator | `observable` |
| enrichment | `enrichment` and `reputation` |
| note | `note` (added to OCSF in 1.9.0) |
| people and teams | `user`, `group` |

Concepts OCSF does not cover (playbooks, playbook runs, paging, queries and driver
capabilities) are anysoar's own models in `anysoar.interface`, kept deliberately small.

### How the models follow OCSF

- **Names and values are OCSF's.** Attribute names, enum values and enum member names
  (captions in `UPPER_SNAKE_CASE`) match the schema. Alerts and cases have separate status
  enums, because OCSF defines different `status_id` values for the two classes.
- **Fidelity is tested against a committed snapshot.** `tests/fixtures/ocsf/schema_snapshot.json`
  is a trimmed copy of the schema, regenerated by `scripts/update_ocsf_snapshot.py`. Tests fail
  if a model declares an attribute OCSF doesn't define, makes an OCSF-required attribute
  optional, or has an enum that differs from OCSF.
- **Only what we use is modelled.** Other OCSF attributes are still accepted and preserved
  (`extra="allow"`), so a full OCSF payload round-trips unchanged.
- **Serialization is OCSF JSON:** enums as integers, timestamps as milliseconds since the
  epoch, unset attributes and empty arrays omitted. `type_uid` is derived as
  `class_uid * 100 + activity_id` and checked when parsing.
- **Profiles are declared.** Detection Finding attributes that come from OCSF's `incident`
  profile (`assignee`, `assignee_group`, `priority_id`, `verdict_id`, `src_url`) add `incident`
  to `metadata.profiles` when set.

### Deviations

- **Unassigned cases are allowed.** OCSF requires an Incident Finding to have an `assignee` or
  `assignee_group`. Unassigned cases are normal in SOAR platforms, so anysoar does not enforce
  this constraint.
- **A case must reference at least one finding.** OCSF requires `finding_info_list` to be
  present; anysoar also requires it to be non-empty. A driver whose SOAR allows cases with no
  alerts should describe the case itself as the single entry.

## Consequences

- Driver authors map their SOAR to a documented public schema rather than to an
  anysoar-specific one, and agent prompts can rely on OCSF semantics.
- Vendor-specific data has a defined home (`unmapped`) instead of leaking into the models.
- Upgrading OCSF is deliberate: regenerate the snapshot, review the diff, adjust the models and
  bump `OCSF_VERSION`.
- Some SOAR concepts will map imperfectly. Each deviation is recorded here rather than
  silently patched into the models.
